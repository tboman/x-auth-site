# X-Auth — Cloud Run deployment (stage 1)

Terraform for running the 8 Go services on GCP Cloud Run, per the staged plan:
Cloud Run now, GKE (ARCHITECTURE.md Appendix B end state) when Enterprise/HIPAA
demands a dedicated cluster.

## What this creates

- **VPC `x-auth`** + serverless VPC connector + Cloud NAT. Cloud SQL and
  Memorystore get private IPs (private services access).
- **Cloud SQL PostgreSQL 16** (`x-auth-pg`) — one instance, one database +
  user per service (`txn_db`, `auth_db`, …), private IP only.
- **Memorystore Redis 7** — shared rate-limit store (§10.5) with AUTH enabled.
- **Secret Manager** — per-service `PG_DSN`, `redis-auth`, and the RS256
  `jwt-signing-key` for authentication-service (§10.1).
- **8 Cloud Run services** — public ingress for transaction-service,
  authentication-service, broker-service; internal-only ingress for the rest.
  All scale to zero by default.
- **8 Cloud Run migration jobs** (`migrate-<short>`) running golang-migrate
  against each service's database.
- **Artifact Registry repo `x-auth`** for CI-built images.

Terraform deploys a placeholder image and then **ignores image changes** —
the GitHub Actions workflow (`.github/workflows/deploy-services.yml`) owns
image rollout: build → push → migrate → deploy → smoke-check.

## Deliberate stage-1 deviations from ARCHITECTURE.md

- **§10.3 service-to-service mTLS**: Cloud Run terminates TLS and has no peer
  certs. Isolation comes from internal-only ingress + VPC instead (callers use
  `egress=ALL_TRAFFIC` through the connector). The `pkg/tlsx` env vars are
  simply unset, so services run plaintext behind Cloud Run's TLS edge.
  Restore real mTLS at the GKE stage, or add IAM ID-token support to the
  HTTP clients.
- **JWT signing key lives in Terraform state** (generated by `tls_private_key`).
  Acceptable with state in a locked-down GCS bucket; the phase-3 key-rotation
  work should move signing to Cloud KMS.
- **Single shared Cloud SQL instance** with per-service databases instead of
  per-service instances — split when load or tenant isolation requires it.
- **Redis transit encryption off** (private VPC only). Enable
  `transit_encryption_mode` when redisx grows TLS support.

## Bootstrap (one-time)

```bash
# 1. Auth + project
gcloud auth application-default login
gcloud config set project xauth-2026

# 2. (Recommended) state bucket — then uncomment the gcs backend in versions.tf
gcloud storage buckets create gs://xauth-2026-tfstate --location=europe-north1 \
  --uniform-bucket-level-access

# 3. Provision
cd deploy/terraform
terraform init
terraform apply
```

First apply takes ~20 minutes (Cloud SQL and the service-networking peering
are slow). Cloud Run services come up on a placeholder image until the first
workflow run.

## GitHub Actions auth (Workload Identity Federation, one-time)

```bash
PROJECT_ID=xauth-2026
PROJECT_NUMBER=$(gcloud projects describe $PROJECT_ID --format='value(projectNumber)')
GH_REPO="tboman/x-auth-site"   # adjust if the repo moves

# Deploy service account
gcloud iam service-accounts create deploy-github --display-name="GitHub Actions deploy"

for role in roles/run.developer roles/artifactregistry.writer roles/iam.serviceAccountUser; do
  gcloud projects add-iam-policy-binding $PROJECT_ID \
    --member="serviceAccount:deploy-github@${PROJECT_ID}.iam.gserviceaccount.com" \
    --role="$role"
done

# Identity pool + GitHub OIDC provider
gcloud iam workload-identity-pools create github --location=global
gcloud iam workload-identity-pools providers create-oidc github-actions \
  --location=global --workload-identity-pool=github \
  --issuer-uri="https://token.actions.githubusercontent.com" \
  --attribute-mapping="google.subject=assertion.sub,attribute.repository=assertion.repository" \
  --attribute-condition="assertion.repository == '${GH_REPO}'"

# Let the repo impersonate the deploy SA
gcloud iam service-accounts add-iam-policy-binding \
  deploy-github@${PROJECT_ID}.iam.gserviceaccount.com \
  --role="roles/iam.workloadIdentityUser" \
  --member="principalSet://iam.googleapis.com/projects/${PROJECT_NUMBER}/locations/global/workloadIdentityPools/github/attribute.repository/${GH_REPO}"
```

Then set two GitHub Actions **secrets** on the repo:

| Secret | Value |
|---|---|
| `GCP_WIF_PROVIDER` | `projects/<PROJECT_NUMBER>/locations/global/workloadIdentityPools/github/providers/github-actions` |
| `GCP_DEPLOY_SA` | `deploy-github@xauth-2026.iam.gserviceaccount.com` |

First deploy: push to `main` touching `services/**` (or run the workflow
manually via *Actions → Deploy services → Run workflow*).

## Custom domains

Map `api.x-auth.com` → transaction-service, `auth.x-auth.com` →
authentication-service, `mcp.x-auth.com` → broker-service, `fido.x-auth.com` →
fido-service with `gcloud beta run domain-mappings create` (or a global external
LB + Cloud Armor when you want WAF/DDoS controls — Appendix B's "Cloud Load
Balancer"), e.g.:

```
gcloud beta run domain-mappings create --service=fido-service \
  --domain=fido.x-auth.com --region=europe-north1
```

After mapping the auth domain, set `auth_public_url` in terraform so the OIDC
issuer matches (`terraform apply -var auth_public_url=https://auth.x-auth.com`).

## Day-2 notes

- **Logs/metrics**: Cloud Logging picks up the structured JSON from pkg/logx
  natively; `/metrics` scraping needs Managed Prometheus when you get there.
- **Production hardening**: `-var db_availability_type=REGIONAL`,
  `-var redis_tier=STANDARD_HA`, `-var min_instances=1` (kills cold starts and
  keeps the purge sweepers running continuously).
- **Scale-to-zero caveat**: the in-process purge sweepers (PURGE_INTERVAL)
  only run while an instance is warm. At `min_instances=0`, rely on TTL checks
  at read time until a Cloud Scheduler job or `min_instances=1` covers it.
- **Enterprise/dedicated tenants**: this module is single-tenant-pool by
  design; the GKE stage (Appendix B) is where per-tenant cluster stamping
  lands.
